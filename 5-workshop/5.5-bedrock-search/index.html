5.5. Building Multi-modal Search Agent with Amazon Bedrock & DynamoDB GSI Catalog

1. How the Multi-modal AI Search Agent Works

In traditional media catalogs, search queries fail when users cannot recall exact keywords. EduMedia AI utilizes Amazon Bedrock (Amazon Nova Pro / Nova Lite) as an intelligent Query Planner coupled with DynamoDB GSI Hybrid Search:

5-Step Pipeline: Semantic Retrieval & Lecture Ranking
Step 1 • Client
User Query
User enters a natural language query in Vietnamese into the search interface.
"find derivative formulas and math notes"
Step 2 • Bedrock AI
Query Planner
Amazon Nova analyzes intent, normalizes entities, and generates a structured Search Plan.
category: study
subject: math
keywords: derivative, math
Step 3 • DynamoDB
GSI Candidate Pool
Queries partitioned index category-index (avoiding expensive full-table scans).
Latency: < 40ms
RCU Saved: 90%
Step 4 • Hybrid Scorer
Hybrid Scoring Engine
Combines semantic vector cosine similarity with exact keyword lexical matching.
Titan V2 Vector: 60%
OCR/ASR Lexical: 40%
Step 5 • Results
Ranked Results
Returns ranked lecture materials with precise jump-to timestamps and OCR bounding boxes.
HTTP 200 OK
Top-K matches

2. DynamoDB Global Secondary Index Architecture (GSI category-index)

Table AgentSysMediaMetadata is configured with GSI category-index:

  • Partition Key (PK): category (study, videos, receipts, pets, people).
  • Candidate Pool & Ordering: Conforms to Serverless Single-Key design; candidate filtering and descending created_at ordering is performed in Lambda memory on the Candidate Pool (capped at 100 recent items), eliminating complex sort key overhead.
  • Projection: ALL.

FinOps & Performance Gains:

  • When the planner identifies category=study, the system performs a targeted Query on partition study instead of a full table Scan → Reduces RCU costs by 90% and cuts latency from 800ms to < 40ms.

3.4. Error Handling, Guardrails & Load-Limit Validation Lab

In addition to happy-path retrieval, the production endpoint (https://1fyafawcuc.execute-api.us-east-1.amazonaws.com) and the backend guardrail test suite (tests/test_demo_guardrails.py) were verified against authentication failures, invalid payloads, protected-record locks, and traffic spikes:

  1. Missing or Invalid X-API-Key (401 Unauthorized):
curl -i -s -X POST "$API_ENDPOINT/api/v1/media/agent/query" \
  -H "Content-Type: application/json" \
  -d '{"user_query": "test"}'

HTTP Response (HTTP/2 401, captured from live API Gateway/FastAPI):

{
  "detail": "Cần đăng nhập hoặc X-API-Key hợp lệ"
}
  1. Unsupported File Format (400 Bad Request) & Over-Limit Upload (413 Request Entity Too Large):
  • Submitting POST /api/v1/media/upload-url with an executable file (malicious.exe, application/x-msdownload) is rejected during MIME/extension validation (endpoints.py):
{
  "detail": "Định dạng tệp không được hỗ trợ. Vui lòng tải ảnh (JPEG, PNG, WebP), âm thanh (MP3, M4A, WAV, FLAC), hoặc video (MP4, MOV, WebM)."
}
  • Requesting a presigned URL with size_bytes: 27262976 (26MB > MAX_PUBLIC_UPLOAD_BYTES = 25MB) is blocked before generating an S3 upload URL:
{
  "detail": "Dung lượng tệp (26MB) vượt quá giới hạn demo cho phép (tối đa 25MB)."
}
  1. Public Demo Sample Protection (403 Forbidden): Calling DELETE /api/v1/media/{file_id} on a record flagged with is_demo_protected: true without the admin override header (x-admin-force: true) returns HTTP 403 to prevent accidental removal of shared sample media:
{
  "detail": "Tệp mẫu được bảo vệ cho người dùng trải nghiệm demo (is_demo_protected: true). Không thể xóa."
}
  1. Rate Limiting (429 Too Many Requests) & Asynchronous Overload Protection:
  • API Layer (slowapi): The semantic query route /api/v1/media/agent/query (and aliases /api/v1/agent/query, /api/search) enforces 20/minute per client IP (while general routes default to 60/minute in rate_limit.py). Exceeding the quota triggers RateLimitExceeded (HTTP 429):
{
  "error": "Rate limit exceeded: 20 per 1 minute"
}
  • Ingest Pipeline Layer (SQS + DLQ): Under ingestion bursts, S3 upload events are buffered in agentsys-ingest-queue and throttled at MaximumConcurrency: 5 on IngestFunction (agentsys-ingest). Messages failing maxReceiveCount: 3 retries are isolated into 3 dedicated Dead-Letter Queues (DLQs) monitored by 7 CloudWatch Alarms.
